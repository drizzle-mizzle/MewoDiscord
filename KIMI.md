## Назначение и стек

Небольшой Discord-бот для дружеского сервера (~20 человек): журнал и автоматизация голосовых каналов, медиа из Telegram/X, сведения о YouTube-видео, ChatGPT-сессии, генерация и механическая обработка изображений/видео, административные команды.

- .NET 10 / C#, `net10.0`.
- Discord.Net 3.20.1, Interaction Framework, Components V2.
- xUnit для тестов; StyleCop и правила `.editorconfig` применяются при сборке.
- Serilog для консоли, файлов и Discord-логов.
- AngleSharp для HTML; YouTube Data API и Return YouTube Dislike.
- CLIProxyAPI sidecar для OpenAI-совместимого доступа через Codex OAuth.
- ffmpeg/ffprobe, yt-dlp и обязательный для YouTube deno.
- Docker Compose для бота и прокси; Windows-публикация через отдельный publish profile.

## Карта кода

- `src/Program.cs` — состав приложения, загрузка состояния, регистрация модулей и команд, подписки gateway, фоновая диспетчеризация и завершение работы.
- `src/Handlers/MessageHandler.cs` — вход сообщений. Сначала независимо запускаются Telegram/X/YouTube preview, затем сообщение может быть потреблено ChatGPT/медиа-маршрутизацией. Ниже в файле лежит недостижимая старая OpenRouter-логика.
- `src/Handlers/ChatGptSessionHandler.cs` — маршрутизация реплаев и пингов, порядок «медиа-сессия раньше ChatGPT-сессии», сериализация ходов замком сессии.
- `src/Handlers/CustomAiActionHandler.cs` — дешёвые системные гейты, затем классификация через instant-модель и запуск первого подходящего процессора.
- `src/AiActionsProcessors/` — `ConvertMedia`, `DownloadVideo`, `EditProfilePicture`, общий `MediaReply` и реестр процессоров.
- `src/Utils/ChatGptClient.cs` — единственный активный путь к ИИ: запросы, история, изображения, instant-запросы и разбор ответов прокси. `ChatGptClient.Responses.cs` добавляет опциональный Responses API с `web_search` и `image_generation`; при `UseWebSearch: true` он основной, Chat Completions остаётся fallback и путём для instant-запросов.
- `src/Utils/ProcessRunner.cs` — единственная точка запуска внешних процессов; аргументы передаются списком без shell.
- `src/Utils/MediaWorkspace.cs` — один глобальный слот тяжёлой медиа-работы, временный каталог, очистка и бюджет диска.
- `src/Utils/FfmpegRunner.cs`, `MediaPlanParser.cs`, `MediaShrink.cs`, `YtDlpRunner.cs` — типизированный план, белые списки, аргументы, probe, выбор качества и пережатие.
- `src/Utils/SocialPost.cs` и `PostMediaHandler.cs` — общая модель соцпоста, сетевые ограничения, скачивание и Components V2; источники подключаются тонкими обработчиками.
- `src/Handlers/VoiceStatusHandler.cs` — журнал сессий, общие события, таймеры длительности и одиночества.
- `src/Handlers/ChannelRenameWatcher.cs` — отдельный актор на канал, восстановление имён и обход rate limit без блокировки журнала.
- `src/MewoDiscord.DevBot/` — read-only REST-утилита для просмотра фактического содержимого Discord-сообщений; gateway не открывает.
- `src/MewoDiscord.Tests/` — автономные unit/fixture-тесты и отдельные ручные сетевые тесты `АИ_*`.

## Потоки данных и состояние

- Все события Discord выполняются в фоне с последним рубежом логирования; сообщения одного канала сериализуются канальным замком.
- Долгие операции не держат канальный замок: ChatGPT сериализуется замком конкретной сессии, тяжёлые ffmpeg/yt-dlp — единственным `MediaWorkspace`.
- Состояние живёт рядом с исполняемым файлом в `state/`, отдельно от read-only `Files/`:
  - `voice_channels.txt` — исходные имена переименованных каналов;
  - `chatgpt_sessions.txt` и `chatgpt_sessions/{id}.json` — индекс, история и последние изображения;
  - `media_sessions.txt` — привязка уточняющих реплаев к исходному медиа и накопленному плану.
- `StateFiles` используется для атомарной записи файлового состояния.
- `config.ini` и `messages.ini` перечитываются на лету; `UseChatGpt` фиксируется при запуске.
- OpenRouter-код, цензор и старый шуточный чат сохранены, но их точки входа отключены. Новые вызовы должны идти через `ChatGptClient`, а не через старый `AiClient`.

## Правила изменений

1. Перед задачей читать относящийся к ней раздел `CLAUDE.md`: там зафиксированы не только инструкции, но и причины неочевидных решений.
2. Сохранять локальный архитектурный стиль: статические handlers/helpers, небольшие процессоры и общие слои вместо преждевременного переустройства на DI.
3. Пользовательские тексты добавлять через `BotMessages` и `messages.ini`; системные ответы оборачивать через `BotEmbeds`.
4. Комментарии и пользовательские сообщения — на русском. Соблюдать `_camelCase` для приватных полей, PascalCase для приватных констант, обязательные скобки и пустую строку после `}`.
5. Модель не должна формировать командную строку ffmpeg/yt-dlp: только типизированный план, проверка и аргументы, собранные кодом.
6. Для нового custom action нужны ini-файл, процессор, регистрация и запись в соответствующем theory-тесте.
7. При изменении поведения обновлять `CLAUDE.md`; если затронуты запуск, команды или пользовательские возможности — также `README.md`.
8. Не запускать боевого бота, сетевые `АИ_*` тесты или DevBot против реального сервера без отдельной необходимости. Не выводить секреты в логи и ответы.
9. После фичи или исправления до коммита/push самостоятельно запускать `feature-finalize`; явная `/feature-finalize` делает то же самое. Порядок и строгий критерий успеха — в `.agents/skills/feature-finalize/SKILL.md`.
